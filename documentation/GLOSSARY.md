# Glossary

Plain-language definitions of every technical/business term this project's design docs use, written for a non-specialist reader. See [CLAUDE.md](../CLAUDE.md)'s non-negotiable rule: every term explained in conversation gets added here, same turn, no exceptions. Design docs keep the full technical detail in their own home file; this file is the quick, jargon-free reference — link here instead of re-explaining a term inline.

## Ownership and sharing

- **Strict tier**: a photo stays visible only to its owner; a revocable viewing grant can be given to someone else, but she never gets an independent, durable copy — the owner can cut off access at any time. See [distributed-sync/OWNERSHIP.md](distributed-sync/OWNERSHIP.md).
- **Leased tier**: a photo can be durably copied onto other people's storage for redundancy, but stays locked (encrypted) with a key only the owner controls — revocable by the owner withholding/rotating that key, even though the locked bytes may still physically exist elsewhere. See [distributed-sync/OWNERSHIP.md](distributed-sync/OWNERSHIP.md).
- **Free tier**: a full, permanent, irrevocable transfer — the recipient becomes a genuine independent owner and can do anything with her own copy, including reshare it further. See [upload-and-share/OWNERSHIP.md](upload-and-share/OWNERSHIP.md).
- **`photo_owners` row**: the database record that says "this specific user owns/can access this specific photo" — sharing adds a new row pointing at the same underlying bytes, it never duplicates them.
- **Tag visibility vs. ownership tier — two separate axes**: a photo's strict/leased/free tier controls who can see the *photo*; a tag's own private/shareable setting controls who can see *that tag* (a name, a label) — independently. A free (fully shareable) photo can still carry a private tag nobody else ever sees.
- **Mutual-acceptance sharing / `open` mode**: the default rule that nobody can share something with you unless you accept it first; a per-user opt-out (`open` mode) lets someone skip that step, currently gated behind an unbuilt safety feature (see "nudity/NCII classifier" below).
- **Blocking**: a user-to-user block that always overrides any other setting — a blocked person can never share with you again, no exceptions.

## Distributed storage and networking (the future "Pillar 1" vision)

- **DFS (distributed file system)**: instead of all photos living on one server, they're spread redundantly across several independent computers (e.g. your own future home NAS plus relatives' own devices), so losing any single one doesn't lose the photos.
- **Node**: one participating computer in the DFS (e.g. one person's home NAS box).
- **DHT (distributed hash table)**: a shared "address book" with no single owner — every participating node holds a small slice of "who's storing what," and a lookup question gets passed node-to-node until it's answered. This is how BitTorrent already finds who's sharing a file; no payment or competition involved, just cooperative bookkeeping. **Kademlia** is the specific DHT algorithm this project's research keeps running into — the one both IPFS and BitTorrent's trackerless mode use.
- **IPFS / Kubo**: a specific, ready-made open-source implementation of a DHT plus content-addressing. **Ruled out for this project's target hardware, 2026-07-29** — Kubo (its reference implementation, renamed from `go-ipfs`) recommends 6 GB RAM, about 6x a Raspberry Pi 3's entire budget. See [distributed-sync/TODO.md](distributed-sync/TODO.md).
- **Content-addressed storage**: a file's "address" is derived from its own contents (a fingerprint/hash of the bytes), so identical files always get the same address and storage is automatically deduplicated. This project's storage already works this way.
- **Erasure coding / secret sharing**: splitting a file into several pieces such that only *some* of them (not all) are needed to reconstruct it — gives redundancy (losing a few pieces is fine) without needing a full copy on every node.
- **Shard**: one piece of a file after erasure coding/secret-sharing has split it up.
- **Replication (storage redundancy)**: the simpler alternative to erasure coding — instead of splitting a file into shards, just keep several full copies (e.g. Garage's default of 3) on different nodes. Costs more raw storage per byte than erasure coding but is simpler to reason about.
- **Proof of Work (PoW)**: the mechanism behind Bitcoin-style mining — everyone competes at a deliberately pointless, hard computational puzzle; winning it first lets you record the next entry in a shared ledger and earns a reward. Secure because cheating is expensive, but that expense is real electricity/hardware cost, which is exactly why it doesn't fit small/constrained hardware.
- **Proof of Stake (PoS)**: an alternative to PoW — instead of a computing race, participants lock up real money/tokens as collateral; cheating loses you the deposit. Far less energy use, but needs a valuable token to stake in the first place.
- **Proof of Useful Work (PoUW)**: the idea of replacing PoW's pointless puzzle with something actually useful (e.g. AI inference). A real research area (back to Primecoin, 2013) but **immature** — research found in 2026 that a real deployed AI-flavored version had zero actual inference happening; nobody's solved cheaply proving the claimed useful work was real. See [distributed-sync/TODO.md](distributed-sync/TODO.md).
- **Blockchain**: a shared, tamper-evident ledger multiple parties agree on without a central authority — solves "who agrees on what's true," a different problem from a DHT's "who has this file."
- **Marketplace** (as used in this project's docs): any system where money changes hands for content or storage — e.g. Adobe Stock selling photographers' work, or Filecoin/Storj renting out spare disk space for payment. Not a reference to Facebook's product of the same name.
- **Tahoe-LAFS**: an existing open-source "Least-Authority File Store" using erasure coding + encryption specifically so no single storage node can read your data and only a threshold of shards is needed to reconstruct it — see [distributed-sync/NETWORK_MECHANISM.md](distributed-sync/NETWORK_MECHANISM.md) for the full research on whether it fits this project.
- **NAT (Network Address Translation)**: the mechanism a home router uses to let every device on a household's private network share one public internet address — the reason most home NAS boxes aren't directly reachable from the internet by a fixed address, and the whole reason STUN/TURN/rendezvous below are needed at all.
- **STUN (Session Traversal Utilities for NAT)**: a small, lightweight protocol that just tells a device what its own public address looks like from the outside, so two devices behind different NATs (a phone on mobile data, a NAS at home) can learn enough about each other to attempt a direct connection — the server's job ends once that's exchanged; no data ever flows through it. This project's pick for the coordination role is **Headscale**, below.
- **TURN (Traversal Using Relays around NAT)**: STUN's fallback for the NAT types a direct connection genuinely can't punch through — a TURN server relays the actual data between the two devices instead of just helping them find each other. Relaying real bandwidth costs real money, unlike STUN's brief handshake, which is why this project treats free STUN-equivalent rendezvous and paid-tier TURN-equivalent relay as sitting on opposite sides of a free/paid line ([distributed-sync/README.md](distributed-sync/README.md)).
- **WireGuard**: a modern, open-source VPN tunnel protocol (already this project's pick for phone↔NAS traffic) — small codebase, fast, and its handshake is stateless, so a connection re-establishes automatically after either side reboots or changes network with no manual reconnect step.
- **Headscale**: a self-hosted, open-source (BSD-3-Clause), Tailscale-protocol-compatible coordination server — this project's STUN-equivalent pick. It only ever helps a phone and the user's own NAS discover each other's address and exchange WireGuard keys, then steps aside once the direct tunnel is up; it never sees the data flowing over that tunnel.
- **coturn**: the standard open-source implementation of both a STUN and a TURN server ("what everyone runs" per the WebRTC ecosystem) — this project's candidate for the paid-tier relay role, since genuinely free public STUN exists but no meaningful free public TURN service does.

## Security and privacy

- **Encryption-at-rest**: data is stored scrambled (encrypted) and only readable by whoever holds the right key — protects the data while it's sitting on a disk, but says nothing about what happens once someone legitimately unlocks it.
- **Decryption key / key-gating**: the "password" that unlocks encrypted data; controlling who holds a valid key is how this project controls who can actually access something, independent of who physically stores the encrypted bytes.
- **JWT (JSON Web Token)**: a compact, signed token format used to prove who's logged in without the server needing a database lookup on every request. This project issues a short-lived JWT (5 min) plus a longer-lived refresh token, both Redis-backed so either can be revoked early — see [policies/AUTHENTICATION.md](policies/AUTHENTICATION.md).
- **Invite delegation**: whether an account that itself joined via an invite can go on to invite further people. This project's rule (decided 2026-08-14): only an admin can grant a nonzero `invites_remaining` to an account, including a newly-invited one — a member's own invite always creates the new account with `invites_remaining=0` (no further delegation) unless an admin raises it afterward. Closes the obvious privilege-escalation path (a member handing out unlimited sub-invites) while still letting "permit this person to invite others" be a real, admin-controlled feature — see `server/app/invites.py`.
- **Refresh token rotation**: each time a refresh token is used at `POST /refresh`, the server issues a brand-new access+refresh pair and immediately revokes (marks single-use, already-consumed) the old refresh token — so a stolen refresh token that's already been used once is worthless to an attacker. This project's `server/app/auth_routes.py` implements it this way (`revoke_refresh_token(jti, ...)` right before minting the new pair).
- **Multi-service deploy skew**: this project's production stack is several separately-built Docker images (`photo-viewer`, `auth`, `detector`, ...) sharing one git repo — rebuilding only the service whose files obviously changed (e.g. `photo-viewer` for a frontend-only change) can leave a *different* service running stale code if a shared dependency (like the JWT payload shape both `server/app/tokens.py` and `app/auth.py` agree on) changed in a commit that landed for a different reason. Root-caused the 2026-08-13 upload-401 bug this way — see `documentation/bugs/repo/under_process/2026-08-13-upload-reports-finished-but-no-files-land-in-folder-or-appear-in-browser.md`.
- **Role claim / role-based access control (RBAC)**: a field inside a signed token (here, JWT's `role`) stating what the logged-in account is allowed to do — this project uses two roles, `member` (only sees their own data) and `admin` (sees everything), built as roles rather than hardcoded to specific accounts, so the same code works regardless of who ends up holding which role. Added 2026-08-07 so `app/`'s photo-viewer (a separate service with no database of its own) can trust a request's role directly from the signed token instead of needing its own DB round trip — see [tags/SCHEMA.md](tags/SCHEMA.md).
- **Passkeys / WebAuthn**: a W3C standard letting a user log in with a device-held key pair (fingerprint, face unlock, or a hardware key) instead of typing a password — verified locally against public keys the app itself stores. No third-party **relying party** (an external identity-verification service) is involved, unlike OAuth, so this stays inside the closed-by-default posture — see [policies/AUTHENTICATION.md](policies/AUTHENTICATION.md).
- **k-anonymity**: a way to query a database without revealing exactly what you're asking about — the client sends only a short prefix of a value's hash, and the server returns every match for that prefix, so it never learns which specific value (e.g. password) was checked. This is how Have I Been Pwned's public breached-password API works.
- **Homomorphic encryption (HE) / secure multiparty computation (MPC)**: cryptographic techniques that let two parties compare or compute on encrypted data *without ever decrypting it*. Real, active research with genuine speed on server-class hardware, but not proven to run on small/constrained devices yet.
- **Biometric data / "special category" data**: under GDPR, data specifically processed to uniquely identify a person (a face embedding used for matching) gets extra-strict legal protection — a plain photo alone does not automatically count.
- **DoS (Denial of Service)**: an attack that doesn't steal or alter data, just makes a service unusable — typically by making it burn far more time/memory/CPU per request than a legitimate request should cost, until it can't keep up with real traffic.
- **Quadratic-time parsing (algorithmic complexity attack)**: a DoS technique that doesn't need a flood of requests — a single crafted input exploits a parser whose work grows quadratically (input size squared) instead of linearly, so a modestly larger input costs disproportionately more CPU time. The `python-multipart` 0.0.20 advisory (see `Dependabot` above) was exactly this: a crafted multipart body could make parsing take far longer than the body's actual size would suggest.
- **Unbounded buffering**: a parser that keeps reading and holding input in memory without an upper limit, so a large or slow-trickling input can exhaust the server's RAM before parsing even finishes — same DoS family as quadratic-time parsing, different mechanism (memory exhaustion rather than CPU burn). This is exactly why `detector/main.py`'s `POST /detect` got its own `MAX_UPLOAD_BYTES` cap (see `documentation/security/THREATS.md` #16) — capping the upload before a full read, rather than trusting the parsing library alone.
- **Parameter smuggling**: exploiting a parser's ambiguity about where one form field ends and another begins, to make the server interpret a single submitted value as two different fields (or hide a field from validation while still having it processed) — lets an attacker sneak a value past a check that only looked at the field name it expected.
- **Arbitrary-file-write (vulnerability class)**: a flaw letting an attacker make the server write a file to a path *they* choose, rather than one the application intended — dangerous because a chosen path can overwrite something sensitive (a config file, a script that later gets executed) instead of just landing in an expected upload directory.
- **Face embedding**: a numeric fingerprint a face-detection model computes from a face — not a photo, but real peer-reviewed research shows it can often be turned back into a recognizable face image, so it isn't automatically "safe" just because it isn't a picture.
- **ISO/IEC 24745**: the real international standard for protecting biometric data at rest — requires that any stored biometric reference be irreversible (can't be turned back into the original), unlinkable (can't be cross-matched across databases), and renewable/revocable. Caveat from the research: published schemes that *claim* irreversibility have been found reversible in practice — don't trust a scheme's own claim without independent adversarial testing.
- **EDPB (European Data Protection Board)**: the EU's top coordinating body for privacy law — every EU country's own privacy watchdog (Sweden's is IMY) meets here to issue official, EU-wide rulings. About as authoritative as EU privacy guidance gets.
- **CJEU (Court of Justice of the European Union)**: the EU's highest court — its rulings are binding across every member state, including Sweden. Relevant here for *Lindqvist* and *Rynes*, the two cases underpinning GDPR's household exemption below.
- **GDPR**: the EU's general data protection law — applies to this project directly, since it's Sweden-based (an EU member state), not just as a hypothetical concern about other people's users.
- **Household / personal-activity exemption**: GDPR's carve-out for purely private/family use (Article 2(2)(c); e.g. keeping your own family's photos on your own laptop) — stops applying the moment an activity reaches out to an "indefinite number of people" outside that private circle, per CJEU case law (*Lindqvist*, *Rynes*).
- **NCMEC**: the US National Center for Missing & Exploited Children, the US body that receives mandatory reports of child sexual abuse material — this project's actual applicable reporting regime is Swedish/EU, not researched yet (see [policies/POLICY.md](policies/POLICY.md)).
- **CSAM (Child Sexual Abuse Material)**: the standard term for illegal content depicting child sexual abuse — moderation (the perceptual-hash blocklist) overrides ownership/sharing terms unconditionally for this category, see [policies/POLICY.md](policies/POLICY.md).
- **NCII (non-consensual intimate imagery)**: explicit images shared or distributed without the depicted person's consent — the category an on-device nudity/NCII classifier is meant to catch before display, see [upload-and-share/ABUSE_MITIGATION.md](upload-and-share/ABUSE_MITIGATION.md).
- **PDQ hash / perceptual hash**: a fingerprint of an image's visual content (not its exact bytes) used to detect known illegal/flagged content even if it's been resized or slightly altered — this project's planned moderation mechanism.
- **XSS (cross-site scripting) / stored XSS**: a web-security bug where user-supplied text gets rendered back into a page as if it were code (HTML/JavaScript) instead of plain text, letting an attacker's input run in someone else's browser session. "Stored" means the malicious text was saved (a tag, a feedback entry) and executes later, for whoever views it — as opposed to a one-off link-based attack. The standard fix is escaping on render: treat user text as data, never as markup, unless deliberately sanitized for the rare case rich formatting is wanted.
- **CSRF (cross-site request forgery)**: a web-security bug where a malicious site tricks a victim's browser into submitting an authenticated request to a different site (e.g. this project's server) using her already-logged-in session, without her intending it. This project's `SameSite=Strict` cookie setting ([policies/AUTHENTICATION.md](policies/AUTHENTICATION.md)) is a strong, largely automatic defense — a `Strict` cookie is never sent along with a request originating from another site at all.
- **Rate limiting**: capping how many requests a client can make in a given time window, to blunt spam/abuse/brute-force attempts. This project uses `slowapi`, keyed by IP address, already live on `POST /login` ([policies/AUTHENTICATION.md](policies/AUTHENTICATION.md)) — the same pattern proposed for a future feedback-submission endpoint.
- **PII (personally identifiable information)**: any data that could identify a specific person — a name, an ID number, an address, a face. Broader than GDPR's own "personal data" term but used interchangeably here; the practical trigger for this project's OCR-in-frame privacy flag ([curation/DETECTORS.md](curation/DETECTORS.md) area D) — a photographed ID card or letter carries PII even though the *photo itself* wasn't "about" a person.
- **Opaque token**: a value with no readable meaning or structure of its own — just a random string. The opposite of a *transparent* identifier like a sequential user id (1, 2, 3, ...) or a real name, where looking at the value alone lets you guess adjacent values, count how many exist, or identify the owner. Used for `users.username` ([plans/deep-singing-firefly.md](plans/deep-singing-firefly.md)) specifically so the per-user storage folder name (`dpfas_media/<username>/`) can't be used to guess who owns it or how many accounts exist.
- **Establishment criterion vs. targeting criterion (GDPR Article 3)**: two independent ways GDPR can apply. The **establishment criterion** (Article 3(1)) triggers because the *controller* (the organization/person deciding how data is processed — here, Joakim/this project) is based in the EU, regardless of where the data subject is. The **targeting criterion** (Article 3(2)) instead triggers because a *non-EU* controller is deliberately offering goods/services to or monitoring people physically in the EU. This project only ever needs the first one — see [policies/POLICY.md](policies/POLICY.md)'s Jurisdiction section for what that resolves.
- **Unsafe deserialization / pickle RCE**: a class of security bug where loading a data file (not running a program) can execute arbitrary code, because the file format allows embedding instructions rather than just values. Python's `pickle` module (which PyTorch's default `.pt`/`.pth` model format uses) is the classic example — loading a malicious model *file* alone, without doing anything else with it, can compromise the machine that loaded it. **ONNX** and **safetensors** are the two common model-file formats designed specifically to avoid this — they can only carry numeric weights, never executable instructions.
- **Face detection vs. face recognition vs. re-identification**: three distinct, often-confused tasks. **Detection** just finds "is there a face here, and where" (a bounding box, no identity). **Recognition/identification** matches a detected face against a *known* identity (an `entities` record, [tags/SCHEMA.md](tags/SCHEMA.md)) — this project does it via a face embedding + nearest-neighbor/classifier, not literally "reading" the face. **Re-identification (re-id)** is the same matching idea applied to non-human subjects (a specific dog, not just "a dog") — see the existing "Animal re-identification" entry below. "Personal detection," as a phrase, doesn't map to a standard term in this space — one of the three above is almost always what's actually meant.
- **Tag provenance / usage disclosure**: a per-tag transparency principle raised 2026-08-04 ([tags/TAXONOMY.md](tags/TAXONOMY.md)) — any tag should be inspectable down to what produced it, its confidence, exactly who can see it, and exactly what it's used for, rather than asking a user to trust an unverifiable claim about her own data.
- **Audience circle**: a reusable, named list of sharing recipients ("Close Friends") a user can share things to as a unit instead of typing each recipient every time — designed 2026-08-05 as its own `entities` type (`entity_type='circle'`), not a tag, precisely because it isn't something the system found out about a photo, distinct from the existing "co-presence/group" tag category (who's *depicted together in a photo*, a content fact, not a sharing target). See [tags/TAXONOMY.md](tags/TAXONOMY.md).
- **Smart Album**: a saved dynamic query over existing tags/entities/embeddings (e.g. "person = Anders AND place = Blidö," ranked by embedding similarity) — not a new tag category or schema concept, same resolution pattern as the audience-circle entry above. The term is borrowed from Apple Photos/Adobe Lightroom, which use it for exactly this shape of feature (a rule-based collection that re-populates itself, as opposed to a manually curated one). Raised 2026-09-06 — see [tags/TAXONOMY.md](tags/TAXONOMY.md)'s "Smart Albums" section.
- **ANPR (automatic number plate recognition)**: detecting and reading a vehicle's license plate out of an image — a specific, legally distinct sub-case of OCR-in-frame ([curation/DETECTORS.md](curation/DETECTORS.md) area D), since a plate resolves to a registered keeper via the national vehicle registry.
- **DPIA (Data Protection Impact Assessment)**: a GDPR-required *process* (not a ban) a data *controller* must carry out before starting processing likely to pose a high risk to people's rights — e.g. combining data from multiple sources in unexpected ways, or using new identification technology. A procedural obligation on whoever controls a given deployment's data, not a statement that the underlying activity is illegal.
- **Zero-shot classification**: sorting something into a category it was never explicitly trained on, by comparing its embedding against a category described only in a text prompt at the moment of use (e.g. "a photo of a blueprint") rather than a fixed label list baked in during training. This is what makes a genuinely **custom**, user-defined category possible with no new model or training pass — see [tags/TAXONOMY.md](tags/TAXONOMY.md)'s custom privacy categories.
- **Purpose-based interpretation (of biometric data, GDPR)**: EDPB Guidelines 3/2019 (§80-81)'s
  reading of Article 9 — a system that classifies a physical characteristic (e.g. estimated age or
  gender) without generating a template used to *uniquely identify* a specific person doesn't count
  as processing "special category" biometric data, even though a face-recognition embedding used for
  identification does. Not unanimous (EDPB's later Guidelines 05/2022 on facial recognition takes a
  broader stance) but the mainstream regulatory position — see
  [curation/DETECTORS.md](curation/DETECTORS.md) area B's age/gender row.
- **Data minimization (GDPR Article 5(1)(c))**: the principle that personal data collected/processed
  must be limited to what's actually necessary for the stated purpose — relevant to this project's
  OCR-in-frame detector ([curation/DETECTORS.md](curation/DETECTORS.md) area D): raw extracted text
  should exist only long enough to run the privacy pattern-match check against it, not be retained
  indefinitely regardless of whether anything sensitive was found.
- **Lookism**: the standard academic/fairness term for bias that privileges certain appearances over
  others — the specific, documented failure mode automated attractiveness-scoring models are shown in
  peer-reviewed literature to reinforce (non-diverse training data skews toward particular
  ethnicities/ages; models show a measurable bias toward idealized features). Relevant to this
  project's flagged "best shot"/attractiveness-scoring idea,
  [curation/DETECTORS.md](curation/DETECTORS.md) area A.
- **ContactsProvider / Contact Picker API**: two different ways an app can get at a phone's contacts, with very different privacy profiles. Android's `ContactsProvider` (`READ_CONTACTS` permission) gives an app the phone's full local contact list in one grant, read entirely on-device — even for contacts whose backing store is a Google account, since Android syncs them down locally first; the app itself never has to call Google. The browser's **Contact Picker API** is narrower: the user explicitly selects contacts (one or more per invocation — `multiple: true` allows several in one picker session, not strictly one-at-a-time) into a web page each time it's invoked, with no standing permission and no bulk access to the rest of the address book. **Desktop support, confirmed 2026-09-04: none** — Chrome on Android M+ only, plus an experimental Safari implementation, no iOS, no desktop browser at all. Raised 2026-09-04 re: `documentation/tags/TODO.md`'s "Contacts import" idea and `security/THREATS.md`'s row 17 — not designed or built either way yet, but the natural fit for this project's mobile case since it has no native mobile app planned (web-only, [VISION.md](VISION.md)); desktop tagging sessions need a separate fallback.
- **PWA (Progressive Web App)**: a website that can be "installed" (added to a home screen/app list, opens in its own window without browser chrome, works at least partly offline) without going through an app store — the alternative this project has repeatedly chosen over a native mobile app, see [curation/IDENTITY_MATCHING.md](curation/IDENTITY_MATCHING.md)'s "Native app avoided as long as possible" standing stance. Built from ordinary HTML/CSS/JS plus two extra pieces: a **manifest** (a small JSON file naming the app, its icon, and how it should launch) and a **service worker** (a background script the browser runs that can intercept network requests to serve cached content offline, and is also what Background Sync/Periodic Background Sync above run through). What a PWA *can't* do that a native app can — enumerate a phone's entire photo library in the background without the user opening it, for instance — is exactly the boundary the File System Access API and Background Sync entries below describe case by case.
- **File System Access API**: a browser API letting a web page (including a desktop PWA) read and write real files/folders on the user's device directly, after an explicit user grant — not just upload/download. Permission is origin-bound and typically re-prompted per session (persistable across sessions via storing the handle in `IndexedDB`), and access ends when all tabs for that origin close. Distinct from the older, universally-supported `<input type="file" multiple>` picker, which every browser supports but only for one-shot selection, not ongoing read/write access. Confirmed 2026-09-04: sufficient for one-time/manual photo selection (e.g. picking photos to contribute to [distributed-sync/](curation/ARCHITECTURE.md) redundancy) from a PWA, without needing a native app.
- **Background Sync / Periodic Background Sync API**: browser APIs letting a PWA's service worker run a task later, even after the page/app is closed (e.g. retrying a failed upload once connectivity returns, or periodically checking for new content). Confirmed 2026-09-04: **iOS Safari supports neither, with no announced timeline** — Android/Chromium browsers do. This is the real, concrete gap between a PWA and a native app for any "runs automatically in the background" feature on iPhone specifically; one-time/manual actions (open the app, do a thing) aren't affected. See [curation/ARCHITECTURE.md](curation/ARCHITECTURE.md)'s PWA-vs-native note.
- **`android:allowBackup`**: an Android app-manifest flag controlling whether the OS's automatic backup service copies that app's local data to the user's Google Drive/Google account. Real, easy-to-overlook leak path for any locally-stored sensitive data (e.g. a future companion app's face-label database) unless explicitly disabled (`allowBackup="false"`) or scoped with a backup-exclusion rule — raised 2026-09-04 in the same contacts-import privacy discussion above.
- **PSI (Private Set Intersection) / PPRL (Privacy-Preserving Record Linkage)**: cryptographic techniques letting two parties learn *only* which of their records match each other, without either side revealing anything about the records that don't match. Real, peer-reviewed research; classic versions target exact-match fields (like a hashed email) rather than fuzzy similarity over continuous biometric embeddings, and — like homomorphic encryption/MPC above — not proven to run on this project's Pi-class target hardware. See [curation/IDENTITY_MATCHING.md](curation/IDENTITY_MATCHING.md)'s cross-household identity-linking discussion.

## Tags and entities

- **Entity**: one reusable record for a recurring person/object/animal/place (e.g. "Dad," "my dog Bella") that many individual photo tags can point to, so searching "every photo of my dog" is one search instead of many separately-worded tags.
- **Bounding box**: the rectangle marking where a tagged person/object/animal sits within a photo. **Built 2026-08-05** ([gui/README.md](gui/README.md)'s tags feature): stored as normalized 0..1 fractions of the image's own width/height, not raw pixel coordinates, so the same box renders in the right place at any display size (a thumbnail, the full lightbox, a different screen) without needing to know which size it was originally drawn against. **`modules/objects.py` (2026-09-04) uses pixel coordinates instead**, a deliberate divergence from the archived GUI's convention above: its bbox's purpose is a later detector cropping straight to that region (`image.crop((x1, y1, x2, y2))`), which pixel ints support directly with no re-multiplication by width/height — the two conventions serve different consumers, not an inconsistency to reconcile.
- **Relationship tag**: a tag that links two other tags together (e.g. "my father," pointing at his own person-entity) rather than describing the photo directly.
- **CardDAV**: an open, decades-old internet standard (RFC 6352) for a client (e.g. Thunderbird, a phone's built-in address book) to read/write a contact list stored on a server, over plain HTTP with an extra `REPORT` verb. Google Contacts, iCloud, and self-hosted servers (Nextcloud, Radicale, Fastmail) all expose a CardDAV endpoint; a client authenticates and pulls the *whole* address book, unlike the browser Contact Picker API's ([security/THREATS.md](security/THREATS.md) row 17) one-contact-at-a-time disclosure. Raised 2026-09-04 by Joakim asking whether "computer contact syncing, like Thunderbird" exists — confirmed it does, researched via web search same day; the desktop-fallback design still has to weigh CardDAV's standing bulk-list access against the list-exposure-minimization reasoning that picked Contact Picker for mobile in the first place.
- **Google People API `resourceName` / `syncToken`**: Google's modern, officially-supported contacts REST API (CardDAV is a legacy compatibility layer over the same underlying data). Every contact has a permanent `resourceName` (e.g. `people/c123...`) that survives a rename — the display name is just a field on the record, not the record's identity. `syncToken`, returned from an initial full fetch, lets a later call ask for only what changed since (edits, and deletions explicitly flagged, not silently dropped) — expires after 7 days, falling back to a full resync. Raised 2026-09-05 answering Joakim's "would renaming a contact break our match" question — the fix is keying our own stored link on `resourceName` (or, for the CSV-import fallback which has no such ID, on email as the closest stable proxy) rather than on the display name.
- **App Password (Google/iCloud)**: a long random string a user generates herself, from inside her own Google/iCloud account security settings (Google requires 2-Step Verification enabled first), for one specific non-OAuth-capable app/protocol to authenticate with over plain HTTP Basic Auth — distinct from her real account password, revocable individually, and requiring no app registration or review by the connecting software's developer at all. **Corrected 2026-09-05** — this session's own earlier text wrongly assumed Google's CardDAV needed a registered OAuth client (the way a "Sign in with Google" button does); researched and confirmed Google explicitly keeps App Passwords open as the supported fallback for exactly this case (its OAuth-only push, effective March 2025, closed the *bare*-account-password path, not this one) — this is the actual mechanism Thunderbird itself commonly uses for Google/iCloud CardDAV, which is why using it never shows an OAuth consent screen.

## Curation and machine perception

- **Embedding / vector**: a fixed-length list of numbers (e.g. 512 of them) a model computes from a photo or a piece of text that captures its "meaning" — two photos that look/feel similar end up with two number-lists that are mathematically close together, even if their pixels or filenames share nothing.
- **Vector database**: a database built to quickly answer "which stored embeddings are closest to this one?" — this project's planned choice is **pgvector**, so embeddings live in the same Postgres instance as everything else rather than a separate system.
- **pgvector**: the PostgreSQL extension VISION.md already names for storing/searching embeddings — open-source, no extra service to run, fits this project's existing "one Postgres instance" pattern (see SCHEMA.md's "relational, not graph DB" decision).
- **Nearest-neighbor search / cosine similarity**: given one embedding, finding the others mathematically closest to it — the actual "find more photos like this one" operation. Cosine similarity measures the angle between two vectors; a smaller angle means more alike.
- **CLIP-style / joint image-text embedding**: a model trained so a photo and a sentence describing it land near the same point in embedding space. This is what makes "show me pictures of my countryside" work as a live search over un-tagged photos — the query text and every photo get embedded into the same space, and the closest photos win — rather than needing every photo hand-tagged "countryside" first.
- **Detector**: one narrow, single-purpose lightweight model that looks at a photo and outputs one specific structured fact (a bounding box, a blur score, a scene label). This project runs several in series per photo instead of one large do-everything model, per POLICY.md's resource-efficiency constraint.
- **The Curator** (proposed name, see [curation/README.md](curation/README.md)): the orchestration layer above the detectors and the embedding index — aggregates what the detectors found, tracks why a suggestion was made, and is what actually talks to the user and incorporates her corrections. Not one neural network; a reasoning/bookkeeping layer, optionally backed by a small local LLM for free-form conversation only.
- **Grounding**: keeping any natural-language explanation tied to facts a separate, verifiable system actually computed (here: the detectors + embedding index), instead of letting a language model invent plausible-sounding claims about a photo. The standard mitigation for hallucination in a system whose credibility depends on being right about what's actually in a picture.
- **RAG (retrieval-augmented generation)**: the general pattern behind grounding above — a language model's answer is generated from real, retrieved facts (a database query result) rather than from the model's own memory alone.
- **Relevance feedback / active learning**: a system that improves its own future suggestions using a user's corrections on past ones, rather than a fixed one-time classification — e.g. "keep this specific blurry photo" should narrow what counts as delete-worthy for photos like it, not just except that one photo.
- **ONNX Runtime**: one shared inference engine that can run many different models' exported files, regardless of which framework (PyTorch, TensorFlow, etc.) originally trained them, as long as they're exported to the standard `.onnx` format. Using it means installing/maintaining one runtime for every detector instead of one per model's original framework.
- **TFLite (TensorFlow Lite)**: a separate, competing model-file-format-plus-runtime ecosystem from ONNX above, built by Google specifically for TensorFlow-trained models running on mobile/edge devices. The two formats don't interoperate — a `.tflite` file needs the TFLite interpreter, an `.onnx` file needs ONNX Runtime, and neither runtime reads the other's format. Relevant here because Google's Coral Edge TPU accelerator only accepts TFLite-format (INT8-quantized) models, while nearly every model this project has picked (DETECTORS.md) is ONNX or OpenVINO IR instead.
- **OpenCV / OpenCV Zoo**: OpenCV is a mature, CPU-friendly computer-vision library (already a dependency of this project's existing prototype); "OpenCV Zoo" is OpenCV's own curated collection of small pretrained models (like the YuNet face detector) distributed for direct use with it, each with its own stated license.
- **YuNet**: this project's picked face-detection model ([curation/DETECTORS.md](curation/DETECTORS.md) area B, built 2026-08-07 as `detector/faces.py`) — a sub-1MB ONNX model from OpenCV Zoo, run through OpenCV's own built-in `cv2.FaceDetectorYN` (no separate ONNX Runtime call needed for this one). Given an image, it returns a list of face detections, each a bounding box plus 5 facial landmarks (eyes, nose tip, mouth corners) and a confidence score — this project only uses the bounding box today, the landmarks are unused. MIT-licensed (the model's own `LICENSE` file, checked directly — not the `opencv_zoo` repo root's separate Apache-2.0, which covers the repo's own code, not each vendored model asset).
- **Variance of Laplacian**: a classic, model-free blur metric — run an edge-detecting filter (the Laplacian) over a grayscale photo, then measure how much the result varies pixel to pixel. A sharp photo has strong, varied edges (high variance); a blurry one smooths edges away (low variance close to zero). This project's `detector/quality.py` uses it for the blur detector, no trained model involved.
- **COCO (Common Objects in Context)**: a widely-used, standard set of 80 everyday object categories (person, car, dog, chair, and so on) that most general-purpose object-detection models — including this project's NanoDet-Plus pick — are trained to recognize. "COCO classes" means specifically those 80 labels, not an open-ended vocabulary.
- **NanoDet-Plus**: this project's picked model (Apache-2.0, [curation/DETECTORS.md](curation/DETECTORS.md) area D) for general object detection — a small, CPU-runnable model trained on the 80 COCO classes above. Ten of those classes are animals, so the same detector pass covers both the `objects` and `animals` tag categories at no extra cost.
- **RQ (Redis Queue)**: a lightweight Python job-queue library built directly on Redis — lets background work (like a detector pass) be queued and processed by a separate worker process, without adding a heavier task-queue system (like Celery) on top of infrastructure this project doesn't otherwise need.
- **Animal re-identification (re-id)**: telling *which specific individual animal* a photo shows (this specific dog, not just "a dog") — the animal-flavoured version of face recognition. Researched 2026-08-03 ([DETECTORS.md](curation/DETECTORS.md) area C): no pretrained model fit this project's MIT/Apache-2.0 license bar, resolved instead by having each household train its own small classifier on its own labels — see the two entries below and [curation/IDENTITY_MATCHING.md](curation/IDENTITY_MATCHING.md).
- **Few-shot learning**: training or adapting a model using only a handful of labeled examples per category, instead of the thousands typically needed — the relevant case here being a household labeling just a few photos of "Fido" before the system can start recognizing him, rather than needing a large pre-existing dataset of that specific dog.
- **Linear probe**: a cheap way to specialize a model without retraining it — freeze an existing embedding model (e.g. CLIP) exactly as-is, and train only a small, fast classifier (e.g. logistic regression) on top of the fixed numbers it outputs. Seconds of CPU time rather than a real training job, since the expensive part (the embedding model itself) never changes.
- **Confidence score**: a 0-1 (or 0-100%) number a detection model reports alongside each result, expressing how sure the model is about that specific box/label — not an accuracy guarantee, just the model's own self-reported certainty for that one instance. What a bounding box's attached percentage actually is.
- **Face clustering**: grouping a set of face embeddings that look similar to each other, with **no known identity involved yet** — distinct from face recognition (matching against an *already-named* person, see the "Face detection vs. recognition vs. re-identification" entry above). Clustering runs first and groups strangers-to-the-system together purely by embedding distance; a human then labels each resulting group (e.g. this project's planned phone-contact-linking gamification drill) — the label comes after the grouping, not before it.
- **DBSCAN**: a density-based clustering algorithm that groups points (here, face embeddings) sitting close together in space, without being told in advance how many groups to expect — points too far from any dense group are left unclustered rather than forced into the nearest one. Well suited to face clustering, where the number of distinct people in a photo library is unknown up front and a lone stranger's face shouldn't be shoved into an existing person's group.
- **NNAPI / execution provider**: the hooks a mobile inference runtime (e.g. ONNX Runtime Mobile) uses to hand a model's math off to whatever hardware acceleration a phone actually has (its GPU, DSP, or a dedicated neural chip) instead of running everything on the CPU — Android's own such hook is called NNAPI (Neural Networks API); Apple's equivalent path is the Core ML execution provider. Purely a speed/battery optimization; it doesn't change what leaves the device.
- **ML Kit**: Google's own bundled SDK for common on-device mobile ML tasks (object detection, face detection, text recognition, etc.) — ships as a closed-source Google Play Services component, not a runtime you can point at an arbitrary model file. Its "on-device" APIs don't transmit images off the phone, but using it means depending on Google's own fixed models and infrastructure rather than the specific MIT/Apache-2.0 models this project already picked — the vendor-lock-in trade-off named in POLICY.md's "Vendor lock-in and openness" section.
- **AAR (Android Archive)**: Android's packaged-library file format — the Android equivalent of a `.jar`, bundling compiled code plus any resources a library needs. A library like ONNX Runtime Mobile ships to Android apps as an AAR, the standard way a Kotlin/Java project pulls in a prebuilt dependency.
- **MobileFaceNet**: this project's picked face-embedding model ([curation/DETECTORS.md](curation/DETECTORS.md) area B) — a small (~1M-parameter) model that turns a detected face into a 128-number embedding for comparing faces to each other. MIT-licensed as a standalone ONNX release, chosen over InsightFace's bundle specifically because InsightFace's own pretrained weights carry a non-commercial-research-only license despite MIT-licensed code.
- **In-process library (vs. a sandboxed process)**: a library like ONNX Runtime Mobile runs inside the same app process as the rest of the code that calls it, not in a separate OS-isolated process of its own. It doesn't add its own sandbox — the protection it inherits is whatever sandbox the host OS already gives the whole app (Android and iOS both isolate each app's storage/process from every other app by default), and it carries no networking code of its own to configure offline.
- **Local-first (sync)**: an app design where the on-device database is the real, complete copy of the data and the app works fully offline — any sync to a server is an optional add-on layered on top, never something the app's core function depends on being reachable.
- **Cluster centroid**: the average of every embedding already placed in one cluster — a cheap stand-in for "what does a typical face in this group look like" used to test whether a *new* face belongs to an existing group without re-comparing it against every face already in that group one by one.
- **OCR (optical character recognition)**: reading/extracting text out of an image — a sign, a label, a document. This project's real privacy angle ([DETECTORS.md](curation/DETECTORS.md) area D): a photo can accidentally contain sensitive readable text (a photographed ID card, a private letter) hiding inside an otherwise ordinary picture, so this needs a conscious privacy read before it becomes a plain research/model pick, same treatment as age/gender estimation.
- **Pose estimation / keypoints**: locating a person's joints (wrists, elbows, knees, shoulders...) as (x,y) coordinates in a photo — the first stage behind any "what is this person doing" detector ([DETECTORS.md](curation/DETECTORS.md) area J). A second stage then interprets the joint positions as an action label (waving, sitting, jumping).
- **Dark pattern / loss-aversion mechanic**: a UI design deliberately built to manipulate engagement rather than serve the user honestly — a countdown timer, a "don't break your streak!" warning, artificial scarcity. This project's [gamified curation sessions](curation/GAMIFICATION.md) explicitly avoid these, per VISION.md's own "motivated tagging, not a chore" principle.
- **Federated learning**: a way for many separate devices/households to jointly improve one shared model without any of them ever sending their raw data anywhere — only model *updates* (not the underlying photos/labels) get combined centrally. A real technique, distinct from and heavier than this project's current "opt-in, anonymized correction export" idea ([curation/GAMIFICATION.md](curation/GAMIFICATION.md)) — flagged as a possible future direction, not designed or adopted here.
- **Edge TPU (e.g. Google Coral)**: a small, dedicated chip built only to run already-trained AI models fast and efficiently, as an add-on to a regular CPU (via USB in Coral's case). Only works with models specifically re-shrunk (quantized, below) and compiled for it — doesn't just run any existing model file as-is, which is why it doesn't drop cleanly into this project's existing ONNX-based picks.
- **Quantization (e.g. INT8)**: shrinking a model by storing its internal numbers in a coarser, smaller format (e.g. 8-bit whole numbers instead of 32-bit decimals) — trades a little accuracy for much less RAM/storage and faster inference, often the difference between "runs on tiny/old hardware" and "doesn't."
- **Non-max suppression (NMS)**: the cleanup step after a detector proposes boxes — when several overlapping boxes claim the same object (common near an object's edges), keep only the highest-confidence one and discard the rest that overlap it past a threshold (measured by IoU below). Runs separately per class, so a genuine person-behind-a-dog case isn't wrongly merged.
- **IoU (Intersection over Union)**: how much two boxes overlap, as a single 0-1 number — the overlapping area divided by the combined (union) area. 1.0 means identical boxes, 0 means they don't touch at all. The standard similarity measure NMS above thresholds against.
- **Distribution Focal Loss (DFL) decode**: how `modules/objects.py`'s NanoDet-Plus model expresses a box edge's position — instead of directly predicting one distance value, it predicts a small probability distribution over discrete distance "bins" (0 to `reg_max`, here 7) via softmax, and the actual distance used is that distribution's weighted average. Four such distributions (one per side: left/top/right/bottom) plus a grid-cell center position produce one box. More expressive than a single regressed number, at the cost of needing this extra decode step.
- **Letterbox (resize)**: resizing an image to fit a model's fixed input size (here 416x416) while preserving its original aspect ratio — scale until the longer side fits, then pad the shorter side with black to fill the rest, centered. Keeps the image from being squashed/stretched, at the cost of needing to track the padding/scale afterward to map results back to the original image's coordinates.

## App-shell framework decision — 2026-09-06

**Superseded the pure-native-Kotlin framing below**: after comparing Flutter, Compose Multiplatform,
Kotlin Multiplatform (native UI per platform), and React Native against this project's actual
constraints, **React Native was chosen** as the app shell for Android + iOS + (potentially) the
NAS-webapp surface. Reasoning chain, in order: (1) Flutter introduces Dart as a new language and is
still Google-primary-funded; (2) Compose Multiplatform stays entirely in Kotlin but is
JetBrains-primary; (3) **React Native's governance moved to a neutral React Foundation under the
Linux Foundation in October 2025**, with founding members Amazon, Microsoft, Huawei, Vercel, Expo,
Callstack, and Software Mansion alongside Meta — the most multi-vendor governance of the four
options, which this project's standing vendor-neutrality principle weighs in its favor despite
introducing JavaScript/TypeScript as a second language. **Language licenses independently verified,
2026-09-06**: Kotlin (Apache-2.0, JetBrains), Swift (Apache-2.0 with a Runtime Library Exception,
Apple, open-sourced 2015), and React/React Native itself (MIT — re-licensed from the original,
controversial "BSD + Patents" license on 2018-02-16, following public pressure including WordPress
Gutenberg dropping React over it) all independently clear this project's MIT/Apache-2.0-only bar.

**The hybrid architecture this implies**: roughly 90%+ of the app (UI, navigation, Smart Album
logic, sync/business logic) stays plain JS/TypeScript. A small number of **Turbo Modules** (or the
newer, faster **Nitro Modules**) — thin Kotlin (Android) + Swift (iOS) bridges — wrap the native
libraries with no official JS binding: OpenCV's DNN calls (no official React Native OpenCV binding
exists) and WireGuard (`wireguard-android`/its iOS equivalent have only community-maintained RN
wrappers, less proven than calling the official libraries directly). This is the standard,
recommended React Native pattern for heavy/native-hardware work, not a workaround — see this file's
Turbo Modules/JSI/Nitro Modules entries below. ONNX Runtime Mobile needs no bridge at all: Microsoft
ships an official `onnxruntime-react-native` package directly.

## Licensing (model/code)

- **MIT / Apache-2.0**: two of the most permissive open-source licenses — anyone can use, modify, and sell software (or a model's weights) built on them, including commercially, with no obligation to share their own changes back. This project's hard bar for any third-party model it uses ([curation/TODO.md](curation/TODO.md)'s 2026-08-03 decision), given its own roadmap toward selling hardware/software later.
- **AGPL-3.0 / copyleft / "network-use clause"**: a stricter open-source license family — using AGPL-licensed code, even just running it as a network service other people connect to (not distributing the code itself), legally obligates releasing your own full source code too. This project excludes every AGPL-licensed model/library it finds (e.g. NudeNet, YOLO26n/YOLO-pose) specifically because that obligation becomes real once its own roadmap reaches selling hardware/software commercially.
- **OpenRAIL-M**: a licensing model used by some newer AI releases — freely usable up to a stated funding or revenue threshold, then a paid commercial license is required past it. Treated the same as AGPL by this project's license bar: a real future obligation given its commercialize roadmap, not a low risk today.
- **ODbL (Open Database License)**: a share-alike license for *databases* specifically, not code or model weights — any database built using ODbL-licensed data must itself stay open under the same terms. Whether that obligation carries over to a *model trained on* an ODbL dataset is legally unresolved, which is why this project treats a model card's self-applied "Apache-2.0" tag as unverified until the underlying training-dataset's own license is checked separately (this exact gap surfaced in the 2026-08-05 action-recognition survey).
- **CC BY 4.0**: a Creative Commons license requiring only attribution — permissive in spirit, but still a separate, distinct license from MIT/Apache-2.0 with its own attribution term to satisfy. The COCO dataset's own annotations carry this license (the images themselves separately fall under Flickr's Terms of Use); same unresolved "does a dataset license constrain the trained model's weights" question as the ODbL entry above, raised 2026-09-06 re: RTMPose ([curation/DETECTORS.md](curation/DETECTORS.md) area J) — an open GitHub issue on the model's own repo (`open-mmlab/mmpose#2106`) shows a user asking this exact question with no clear maintainer resolution found.
- **GPL-2.0 / LGPL / copyleft on distribution (distinct from AGPL's network-use clause above)**: plain GPL's copyleft obligation triggers on *distributing* the software (e.g. shipping an app that bundles GPL code to a user's device) rather than only on running it as a network service — relevant to a native app specifically, since an APK handed to a user's phone is a distribution regardless of whether the app ever talks to a network at all. LGPL relaxes this for *dynamic* linking (a separate shared library can stay proprietary) but not static/bundled linking. This is why, e.g., a GPL-licensed video-playback library (`libvlc`/VLC-Android) doesn't clear this project's MIT/Apache-2.0 bar even though nothing about it involves a server.

## Hardware and manufacturing

- **PCB (printed circuit board)**: the flat board that physically holds and wires together a device's chips/components. A "custom PCB" means designing this board from scratch for a specific product, rather than reusing an existing single-board computer like a Raspberry Pi as-is.
- **Modular (hardware)**: a design where separate functional pieces (e.g. a 5G modem, a storage bay, a GPU module) plug into a common board as independent, swappable units, instead of being fixed/soldered into one fixed design — lets a buyer customize or later upgrade just one piece.
- **Hot-swappable**: a component (typically a drive/SSD) that can be physically removed and replaced while the device keeps running, with no shutdown/reboot needed.
- **Industrial design**: the discipline of designing a physical product's actual look, feel, and form factor (as distinct from its internal engineering) — researched 2026-08-06 as the specific lever reported to determine whether a technically-capable device reads as approachable to non-technical buyers or stays a niche/enthusiast product. See [distributed-sync/HARDWARE.md](distributed-sync/HARDWARE.md).
- **Crowdfunding / pre-order** (as a hardware funding model): raising money from future customers before a product is manufactured, by taking payment upfront in exchange for an eventual unit — used by open-hardware precedents like Turing Pi 2 and ZimaBoard 2 (researched 2026-08-06) to reach production without needing outside investment first.
- **Konsumentköplagen**: Sweden's Consumer Sales Act — gives anyone who buys a new physical good a minimum 3-year statutory right to complain about an original/manufacturing defect, with the burden of proof on the seller, independent of and not replaceable by any voluntary warranty the seller chooses to offer on top. Researched 2026-08-06 — see [income/TODO.md](income/TODO.md).

## Performance/benchmarking

- **CPU time vs. wall-clock time**: CPU time is how long the processor actually spent computing (`user` + `system` time); wall-clock time is how long the whole thing took by a clock on the wall, which also includes waiting (disk I/O, network, another process holding the CPU). For a synchronous, single-process service like this project's `detector/`, a before/after CPU-time delta around one function call cleanly attributes cost to that call — a wall-clock delta wouldn't, since it could be inflated by unrelated waiting. `resource.getrusage(resource.RUSAGE_SELF)` (Python stdlib) is what `documentation/plans/tingly-humming-pudding.md`'s per-detector benchmarking reads this from.
- **RSS (resident set size) / peak RSS**: how much RAM a process actually has loaded into physical memory right now (distinct from how much it's *allocated*, which can be more). "Peak RSS" is the highest that figure has been since the process started — a cumulative, whole-process number, not attributable to any single request or function call the way CPU time is. This project's detector benchmarking reports it once per batch, explicitly not broken down per-detector, because most of it is YuNet's one-time model-load cost rather than a repeating per-photo cost.
- **multipart/form-data**: the standard HTTP encoding for a request body that includes a file upload (as opposed to plain JSON) — the body is split into named parts by a boundary marker, each part carrying its own small header (e.g. a filename, a content type). `app/benchmark_detector.py` builds this by hand with the Python standard library rather than adding a new HTTP-client dependency just for one internal benchmarking script.

## Storage and file transfer

- **sshfs**: mounts a remote directory (reachable over SSH) as if it were an ordinary local folder — reads/writes go over the existing SSH connection (SFTP under the hood), no separate server-side support needed beyond SSH access that's already there. Lets a local file picker (e.g. a browser's upload dialog) navigate into files that physically live on a remote machine.
- **EXIF**: metadata a camera/phone embeds directly inside a photo's own file bytes (capture date, camera model, GPS coordinates, orientation) — distinct from this project's own `tags` table, which holds curation-specific labels (people/places/objects/occasion) this app itself creates or a user adds. The archived `app/main.py` used `ImageOps.exif_transpose` to rotate a thumbnail correctly before generating it; `modules/test_main.py` (2026-09-04) reads it directly via `PIL.Image.getexif()`/`ExifTags` to display it (camera/settings/GPS) — not a `modules/` detector function, just this dev tool's own display code, so it stays outside the no-shared-code-with-`app/` rule without needing to import the archived version.
- **X server / pixmap / `BadAlloc`**: on Linux, the X server is the process that actually owns the screen and every window's on-screen pixels; a GUI toolkit like tkinter asks it to allocate a **pixmap** (off-screen image memory it manages) for each image a program wants to display. `BadAlloc` is the X server's own error when it refuses that request — a server-side resource ceiling, not a Python-level out-of-memory. Found 2026-09-04: `modules/test_main.py` rendering 100 photos at once asked for ~300MB of pixmap memory in one go and hit this — fixed via pagination, confirmed resolved same day, see `documentation/bugs/repo/fixed/2026-09-04-test-main-py-x-badalloc-rendering-100-photos-at-once-SOLVED.md`.
- **EXIF orientation auto-rotation, library-inconsistency gotcha**: found 2026-09-04 building `modules/test_main.py` — `cv2.imread` (used by `modules/objects.py`'s detector) automatically rotates a JPEG's pixel data to match its EXIF orientation tag; `PIL.Image.open` does *not*, unless `ImageOps.exif_transpose` is called explicitly. Left inconsistent, a bounding box computed against `cv2`'s rotated image lands on the wrong content when drawn onto PIL's un-rotated one — correct predictions, wrong placement, exactly what happened before this was caught. `modules/test_main.py`'s `_annotate()` now asserts the two libraries' image dimensions match after `exif_transpose`, so a future recurrence fails loudly instead of silently misplacing boxes again.

## Tooling

- **JUnit XML**: a standardized machine-readable test-report format (originally from the Java testing tool JUnit, now a de facto standard other languages' test runners emit too) — a `<testsuite>` element carries how many tests ran, passed, failed, errored, or were skipped, plus total duration, as XML attributes rather than parsed-from-terminal-text. `pytest` can emit it natively via `--junitxml=path`, no extra plugin needed. Used by `tools/test_results/` (see [TEST_RESULTS.md](tooling/TEST_RESULTS.md)) instead of re-parsing pytest's `-q` summary line, whose exact wording isn't a stable contract to parse against.
- **pytest marker**: a `@pytest.mark.name` tag on a test function, letting a run selectively include/exclude tests by tag (`-m "not docker"` runs everything except tests marked `docker`). This project's `server/tests` suite uses a `docker` marker on its one slow, real-`docker build` test so the fast default run skips it.
- **git hook / `core.hooksPath`**: a script git runs automatically at a specific point (e.g. `pre-commit`, just before a commit is created) — can block the commit entirely by exiting non-zero. Git only looks in `.git/hooks/` (not repo-tracked) unless `core.hooksPath` is pointed elsewhere; this project's tracked hook lives at `.githooks/pre-commit` and needs that one-time `git config core.hooksPath .githooks` per clone to actually run.
- **Append-only ledger (jsonl)**: one JSON object per line, in a file that's only ever added to, never rewritten — `doc_metrics`, `commit_cost`, and `test_results` (see [TEST_RESULTS.md](tooling/TEST_RESULTS.md)) all use this shape so a past row's meaning never silently changes underneath later analysis.
- **ES module (`<script type="module">`)**: a browser-native way to split JavaScript across files with real `import`/`export` between them, without needing a bundler or build step — distinct from this project's current classic (`<script src="...">`) style, where every file just shares one global scope. Raised 2026-08-05 for `app/`'s frontend (currently one 800+ line `app.js`); not yet adopted — flagged as a same-shaped-but-separate refactor from feature work, to do with its own focused pass rather than alongside live interactive-UI changes.
- **CVE (Common Vulnerabilities and Exposures)**: a public, numbered catalog entry for a known security flaw in a specific piece of software. **GHSA (GitHub Security Advisory)** is GitHub's own equivalent identifier, often referencing the same underlying flaw. A CVE/GHSA existing for a package version doesn't mean this project is exploitable by it — it means that version has a documented flaw, which is why pinned versions matter (see `python-multipart`/`pillow` bumps, `documentation/changelog/2026-08-07T19-55-33Z-*`).
- **Dependabot**: a GitHub-hosted (not self-run) bot that scans this repo's dependency manifests weekly against the CVE/GHSA databases and opens alerts for flagged versions — originally configured 2026-08-07 in `.github/dependabot.yml` for pip/`uv`/Docker across root, `server/`, `detector/`. **Re-checked 2026-09-06 (via `git show android-app-test1:.github/dependabot.yml`, without needing to check that branch out): the file has since narrowed to only `pip` for `/modules`** — the description above predates the native-app pivot's archival of `server/`/`detector/`. No `npm`/`gradle`/Swift Package Manager entry exists yet for the React Native app shell or its Kotlin+Swift native modules, a real gap flagged in [policies/WORKFLOW.md](policies/WORKFLOW.md)'s dependency-freshness section. GitHub-exclusive — disappears entirely if this repo ever moves to a self-hosted git server, see that same section's forward-looking note on what replaces it then.
- **OSV (Open Source Vulnerabilities) / osv.dev**: a free, open vulnerability database aggregating CVEs, GitHub Security Advisories, and ecosystem-specific advisories into one queryable format, indexed by package + ecosystem + version range rather than free text. **OSV-Scanner** (Google, Apache-2.0) is the CLI tool that reads a project's lockfiles and checks them against it. Two very different privacy shapes, verified 2026-09-06: its **default mode** calls OSV.dev's live API per scan (package name/version/ecosystem/hash leave the machine each time — not source code or user data, but a real network call each run); its **offline mode** downloads the vulnerability database once as a local file (like an antivirus signature-database update), after which every scan runs entirely locally with zero network calls — the only mode consistent with this project's closed-by-default rule.
- **NVD (National Vulnerability Database)**: the US government's official, free CVE database and feed (nvd.nist.gov) — authoritative but raw: no automatic matching against any specific project's actual dependency list, so subscribing to it directly means manually cross-referencing every new CVE yourself. This is why a scanning tool (OSV-Scanner, Dependabot, Dependency-Track) that does that matching automatically is a meaningfully different, more practical thing than "subscribing to CVEs" alone.
- **Renovate**: the most capable host-agnostic Dependabot equivalent (works against self-hosted Gitea/Forgejo git servers, not just GitHub) — **checked 2026-09-06 and excluded**: it's AGPL-3.0-licensed, and self-hosting it as a running bot against this project's own future git server is exactly the "network service" scenario that license's obligation targets (same reasoning already applied to exclude NudeNet/YOLO26n elsewhere in this file), not a low-risk edge case.
- **SBOM (Software Bill of Materials)**: a standardized, machine-readable manifest of every component (library, version, license) that goes into a piece of software — CycloneDX and SPDX are the two common formats. The input format tools like OWASP Dependency-Track continuously monitor against vulnerability databases, rather than re-scanning raw lockfiles each time.
- **OWASP Dependency-Track**: an Apache-2.0, OWASP Foundation-governed (a nonprofit, not a single company) self-hostable platform (Docker Compose deploy) that ingests a project's SBOM and continuously cross-references it against NVD/GitHub Advisories/OSV — flagged 2026-09-06 as a candidate CVE-monitoring answer for whenever this project's self-hosted-git plan happens, alongside OSV-Scanner's offline mode above.
- **Saturation (HSV/HSL)**: the "S" channel in the HSV/HSL color model — how vivid/colorful a pixel is, independent of its brightness or hue. Low saturation looks gray/washed out, high saturation looks vivid. The standard term (every photo editor's "Saturation" slider uses it) for what this project's `documentation/data-modeling/QUALITY_METRICS.md` calls `saturation_percent`, chosen over a project-specific name like "monochrome" precisely because it's already familiar.
- **EV (exposure compensation)**: a photography convention for describing how much brighter or darker an image is than "correctly" exposed, as a signed value — negative EV = darker/underexposed, positive EV = brighter/overexposed, 0 = balanced. Shown on virtually every camera and phone camera app as a +/- dial or slider. `documentation/data-modeling/QUALITY_METRICS.md`'s `exposure_percent` column follows this same signed convention rather than inventing a new one.
- **Filesystem metadata / stat data**: the file-on-disk facts a POSIX `stat()` call returns (what Python's `os.stat()` wraps) — size, permission bits, and three timestamps that are easy to mix up: `mtime` (content last modified), `ctime` (metadata last *changed* — renamed, permissions altered, etc. — **not** creation time, a common misconception, especially on Linux), and `atime` (last accessed). A true creation/**birth** time exists only on some filesystems (ext4/xfs/btrfs), fetched via the `statx(2)` syscall's `STATX_BTIME` field — **not** a Python stdlib function despite "`os.statx`" being the shorthand this project used before building it: Python's `os.stat()` never exposes a birth time on Linux at all (only macOS/BSD do, via `st_birthtime`), so `modules/pictures.py` calls `statx(2)` directly through `ctypes` instead. Distinct from EXIF (metadata embedded in the image bytes themselves, e.g. camera-recorded capture date/GPS) — `documentation/data-modeling/PICTURES_PIPELINE.md`'s `file_metadata` column is this stat data, not EXIF.
- **`uv`**: a fast Python package/dependency manager (an alternative to plain `pip`) that produces a lockfile (`uv.lock`) pinning exact resolved versions. Only `server/` (the auth stack) uses `uv` in this repo; `detector/` and the root app use plain `pip` with a hand-pinned `requirements.txt` instead — see `documentation/photo-server/TOOLCHAIN.md`.
