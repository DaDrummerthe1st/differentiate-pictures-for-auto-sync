# Lightbox shows previous photo when clicking a not-yet-loaded thumbnail

Status: **fix implemented 2026-08-13, pending live verification on the real server**. Full chronological trail — don't overwrite conclusions.

## Symptom

Joakim, 2026-07-18: clicking a grid thumbnail whose own image hasn't finished loading yet opens the full-screen lightbox popup, but it shows the *previous* photo (whatever was last viewed), not the one just clicked. Confirmed (via a clarifying question) the wrong content shows in the lightbox popup itself, not in the small grid tile.

## Investigation log

1. Static read of `app/static/app.js`'s `onThumbClick` -> `openLightbox` path: `onThumbClick` reads `thumbEl.dataset.idx` directly off the clicked DOM element (set once at render time in `renderTree`, not tied to whether that element's own `<img>` has finished loading) and passes it to `openLightbox(idx)`, which synchronously sets `currentLightboxIndex = idx` and `lbImg.src = /original?p=...allImages[idx]`. No obvious async gap or stale-closure in this path on a first read.
2. Checked whether a layout-shift misclick (grid reflowing as thumbnails lazy-load, causing a click to land on the wrong DOM element) could explain it: ruled out - `app/static/style.css`'s `.thumb` has `aspect-ratio: 1 / 1` explicitly set, so grid cells are reserved at fixed size before their image loads; no reflow to cause a misclick.
3. Checked whether `allImages`/`renderTree` could be rebuilding mid-session (which would desync a previously-read `idx`): `loadTree()` (which calls `renderTree`) is only ever called once, from `enterGallery()` at page load - no other caller found, so this shouldn't be re-running during normal browsing.
4. No root cause identified yet from static reading alone.
5. **Symptom changed after today's redeploy** (Joakim, 2026-07-18, post `d147c04` deploy): clicking a not-yet-loaded thumbnail now shows *nothing at all* - not even the broken-image placeholder icon a failed `<img>` load normally shows. Previously it showed the *previous* photo instead. Not yet understood whether this is the same underlying bug presenting differently (e.g. now correctly failing to load the wrong content, where it previously somehow rendered stale content), or a distinct regression introduced by one of today's other changes (the `docs_url=None` fix, the schema-init lifespan handler, or something else entirely unrelated). Needs a fresh live repro - don't assume continuity with the earlier "previous photo" symptom.

6. **Root cause found, 2026-08-13 (Joakim's own fresh recollection, then confirmed by code reading)**: Joakim's current memory of the symptom is narrower than entries 1-5 above — not "wrong photo" or "nothing at all", but that the lightbox visibly gets *stuck showing the previous photo* while the newly-clicked one is still loading, i.e. a plain slowness/no-feedback problem, not a stale-index or server-mismatch bug. Confirmed against the live code: `openLightbox`/`lightboxStep` (`app/static/app.js:769-789`) set `lbImg.src` to the new `/original?p=...` URL and immediately unhide the lightbox, with no loading/spinner state and no clearing of the previous `src` first (`app/static/style.css` has no lightbox loading-indicator rule at all — grepped, none found). Standard `<img>` behavior is to keep rendering whatever was last successfully decoded until the new `src` finishes loading, so during that fetch the lightbox correctly *looks* like it's still showing the old photo — because it is, on purpose, just without any indication that a new one is on the way. This is worsened by `/original` (`app/main.py:585-590`) serving the raw full-resolution file straight off disk via `FileResponse`, no resizing/compression — for this project's CD/DVD-ripped source material that can be a multi-MB JPEG or larger, so the wait is long enough to read as "stuck," not just a brief flicker.
7. This reframes the bug from "shows wrong content" to "shows stale content with no loading feedback, long enough to be mistaken for wrong/broken content." Entries 1-5's stale-index and server-mismatch theories are not ruled impossible, but there is now a confirmed, simpler, sufficient explanation that doesn't require either.

## Leading theory (confirmed sufficient, 2026-08-13)

No loading indicator on lightbox open/step + no downscaling on `/original` → the previous photo stays visible for however long the new full-resolution fetch takes, which reads as "wrong/stuck photo" to the user. Entries 1-5's async/stale-index/server-mismatch theories remain unconfirmed and are no longer the leading candidates, but haven't been actively disproven either — worth keeping in mind if a fix here doesn't fully resolve what Joakim sees live.

## Fix implemented, 2026-08-13

`app/static/app.js`: new `emptyLbImg()` calls `lbImg.removeAttribute("src")` (not `src = ""`, which is a known footgun — some browsers reload the current page URL when an `<img>`'s `src` is set to an empty string) — this actually drops the previous photo's decoded bytes, not just visually hides them, so the browser can release the memory immediately rather than holding it until the next photo overwrites it. Called from three places: `showLbLoading()` (itself called at the top of `openLightbox`/`lightboxStep`, before the new `src` is set, so there is never a frame where the old photo is visible), and from `closeLightbox()` directly (first iteration of this fix only handled open/step via a CSS `visibility` toggle and left `closeLightbox()` untouched — Joakim caught that the old photo was still sitting in the DOM after Escape/closing, not actually gone). A `#lbSpinner` element (`index.html`, styled in `style.css`) shows while `lbImg` is empty and hides on its `load`/`error` event.

Not yet verified against the real deployed app (`docker-compose.prod.yml`'s `photo-viewer` service bakes `app/static/` into its image via `COPY app/ ./app/` in `Dockerfile` — a plain restart won't pick this up, needs `--build`). Verify live, throttled network, per this repo's `CLAUDE.md` deployment hand-over rule (`DEPLOYMENT.md` commands are written for Joakim to run, not run by the AI session).
