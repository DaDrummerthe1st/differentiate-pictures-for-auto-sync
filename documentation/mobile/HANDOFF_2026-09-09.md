## What was built this session (all now committed and pushed - `8bca8bc`, `240eda2`)

1. **On-device face detection + embedding pipeline** —
   `android/app/src/main/java/com/dpfas/photobrowser/facerecognition/`. `YuNetFaceDetector` (decode
   math ported directly from OpenCV's own `face_detect.cpp`, since the raw ONNX graph has no
   equivalent of OpenCV's `FaceDetectorYN` convenience wrapper) + `MobileFaceNetEmbedder` (512-d
   embeddings — corrected from the 128-d figure `DETECTORS.md` previously stated, which described
   MobileFaceNet variants generally, not this exact vendored file; preprocessing verified against
   InsightFace's own `recognition/arcface_torch/inference.py`, not assumed). Runs via **ONNX
   Runtime Mobile**, not MNN — see the runtime-conflict note below. Models vendored + licensed in
   `android/app/src/main/assets/models/LICENSES.md`. Runs automatically over the visible gallery on
   launch, logs to Logcat (`FaceScan` tag), shows a summary Toast.
2. **Fixed a real bug**: `PhotoBitmapLoader`'s bounds-probe decode had the exact same elvis-operator
   shape as the already-fixed 2026-09-06 photo-grid bug (`decodeStream` returns null in bounds-only
   mode by design, so `?: return null` fired on every call, silently zeroing every face count) —
   despite having read the original bug file earlier in the same session. Filed, fixed, closed
   (`documentation/bugs/claude-bugs/fixed/2026-09-09-repeated-the-2026-09-06-...md`), and a new
   WORKFLOW.md rule added: check `documentation/bugs/` before writing another bounds-only decode.
3. **Bounding-box overlay, fullscreen only** — a "Show detected faces" checkbox (off by default),
   never in the grid (the existing `mobile/UX_FLOWS.md` "badge, not drawn boxes" decision was never
   touched — confirmed by rereading `PhotoAdapter.kt`/`grid_item_photo.xml`).
4. **Similar-faces search** — tap a face box in fullscreen -> grid of other photos with similar
   faces, ranked by cosine similarity (`FaceSimilarity.findSimilar`), matching the nearest-neighbor
   mechanism already designed in `curation/IDENTITY_MATCHING.md` (Joakim confirmed this over pulling
   in the unmerged DBSCAN-clustering branch, a different mechanism for a different purpose - see
   below).
5. **Two throwaway swipe-triage demos** (`triage/` package, reachable via the main grid's overflow
   menu), from the design spec relayed by session `differentiate-pictures-for-auto-sync-26`:
   multi-select + bottom action bar, and per-tile Tinder-style swipe. Grid-only, Remove/Organize
   backed by Toast+Log stubs per Joakim's explicit call (fake the persistence, but TDD still applies
   to the demo logic itself) - `TriageSelection`/`SwipeGesture`/`TriageSwipeController` are all pure
   and unit-tested.

Verified end to end on `Motorola_Moto_G54_5G` (emulator-5554): 78/78 tests green, clean install,
109 faces detected across 107 photos, no crashes.

## Runtime conflict — resolved (deferred), 2026-09-09

An unmerged worktree branch (`worktree-android-native-ai-stack`, commit `8dfac99`, Sep 6) had
independently picked **OpenCV** as the on-device runtime, one day before `android-app-test1` picked
**MNN** (`a2d6281`) with no awareness of each other. Separately, this session found MNN's own Maven
AAR ships no x86_64 native libs at all (arm64/armv7 only) and no usable Java API in the artifact —
so it can't run on this emulator regardless. The pipeline above uses a **third** option, **ONNX
Runtime Mobile**, purely as the pragmatic unblocking choice. **Joakim's call: defer** — don't
standardize now, keep ONNX Runtime Mobile under the working code as-is, revisit runtime strategy in
a dedicated session. Full detail in `TODO.md`'s matching 2026-09-09 entry - treat as still fully
open, not settled by precedent of "most code currently uses ONNX."
