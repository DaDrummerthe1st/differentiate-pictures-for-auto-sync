# Hardware — photo-server

The machine this runs on. It also hosts the ZFS pool other things depend on, so photo-server is containerized (Docker Compose) rather than installed natively — a native install's dependencies could collide with, or need root access shared with, whatever else already runs against that pool. See [README.md](README.md) for the resulting non-negotiable.

The `192.168.1.1` gateway address is inferred from the dev workstation's own `ip route` (same `192.168.1.0/24` subnet as the server) — not read directly off the server or the router itself, per the "physically separate machine" note below. Confirm on the server directly (`ip route | grep default`) if this ever needs to be certain rather than inferred.

**Router admin UI has no valid TLS** (noted 2026-07-17): `https://192.168.1.1` does not present a trusted certificate — expected for a home router's self-managed admin interface, LAN-only exposure, not something to "fix." Flagging so a future session doesn't mistake it for a live problem.

**DDoS / resource-exhaustion risk accepted, not mitigated** (2026-07-17): raised while setting up the P0 internet exposure — a real volumetric DDoS can't be stopped by anything configurable on an EdgeRouter X or in this app; that needs upstream mitigation (ISP-level, or a CDN in front), out of scope for this project's closed/no-cloud-APIs posture. Accepted as a standing risk of self-hosting on a residential line at v1 scale, not a today-fix. What IS mitigated: 2026-07-17's auth-gating work means almost every resource-expensive route (thumbnails, downloads, the full filesystem tree walk) requires a valid session, closing off anonymous abuse of those specifically — see DEFERRED.md for the two routes that remain anonymously reachable and why they're low-risk.

**This is a physically separate machine from wherever an AI session (or Joakim) edits code or runs a dev shell.** Confirmed 2026-07-15: dev/build work (including any Claude Code session) happens on a different Ubuntu machine; only the table above describes 192.168.1.10 itself. Don't infer which host you're on from `uname`/OS match alone — check the IP or ask.

**The memtest gate does not actually stop the stack from running, found 2026-07-23**: the gate's wording only prevents a *manual* `docker compose up`. `docker-compose.prod.yml`'s own restart policy brings the production containers back automatically on every host reboot regardless — confirmed via a 2026-07-23 incident where the stack silently came back up (and stayed serving `photos.reuterborg.se`) across several reboots during dock/BIOS troubleshooting, with nobody running `docker compose up` by hand. If the gate is meant to actually keep this host quiet pending a memtest pass, that requires a deliberate `docker compose -f docker-compose.prod.yml down` before any planned reboot, not just avoiding the `up` command — this hasn't been done as standing practice, only noted here so it isn't assumed to already be true. See `documentation/bugs/repo/under_process/2026-07-23-server-dropped-to-emergency-mode-after-reboot-for-memtest.md` for the full incident.

**Dock interface choice: SATA, not USB** (decided 2026-07-23, no prior record existed of why USB had been chosen originally): the dock supports both a USB and a native SATA connection to the host; only SATA is connected. Native SATA avoids USB-to-SATA bridge-chip reliability issues (command translation, SMART passthrough) that the wider ZFS community advises against for pool drives — web-search-confirmed, not assumed. Do not connect the dock's USB cable at the same time as SATA — risk of the same physical drives being exposed twice under different device paths, unverified for this specific dock's internal design and not worth testing.

**BIOS boot-priority quirk, found 2026-07-23**: this board's `Advanced BIOS Features > Hard Disk Boot Priority` (Award BIOS, `DEL` to enter setup) appears to reset or reorder whenever the dock's drive count changes, sometimes ranking a generic `Bootable Add-In Cards` entry above the actual boot drive (`Ch 4 M: ST3250318AS`, on the add-in SATA card) — causing a hang (blinking cursor after the splash screen, no further output) instead of booting through. If this happens again after any case-opening or dock reconnect: enter BIOS setup, reorder `Ch 4 M: ST3250318AS` to the top of Hard Disk Boot Priority, save (F10) and exit — before assuming a new hardware fault.
