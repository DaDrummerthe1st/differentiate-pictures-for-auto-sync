## Jurisdiction

- **This project runs primarily in Sweden — Swedish tax law and GDPR (Sweden is an EU member state) are the applicable legal frameworks, settled, not to be re-derived or questioned per-session.** GDPR applies to this project directly (not as a hypothetical "some EU user might exist" case — Joakim and the project itself are Sweden-based), and any tax-obligation question (e.g. the marketplace idea, [income/TODO.md](../income/TODO.md)) needs Swedish/EU-specific research (Skatteverket rules, EU VAT/moms on digital goods), not US-centric citations. This does not by itself resolve the "Legal reporting obligations" item below — that still needs its own Sweden-specific legal check, not an assumption that a GDPR/Swedish-tax framing also answers illegal-content reporting duties.
- **Whose responsibility when a Swedish user tags/shares a photo of a non-Swedish, non-EU friend — resolved 2026-08-04, GDPR Article 3(1)'s "establishment criterion".** GDPR's territorial scope has two independent triggers: 3(1) (the *controller's* establishment is in the EU — applies regardless of where the data subject is) and 3(2) (the controller is outside the EU but targets EU-based subjects). This project only ever needs 3(1): because the controller (Joakim, operating this project) is Sweden-established, GDPR governs *every* processing decision this project makes, for *any* tagged individual, regardless of her nationality or physical location — a Swedish user tagging an American or Thai friend doesn't create a different, weaker legal regime just because the friend is outside the EU. Responsibility sits with the controller, not with whichever jurisdiction the tagged person happens to hold citizenship in. This is a data-subject-location question, distinct from the [household/personal-activity exemption](../GLOSSARY.md) (which turns on how widely something is shared, not who's in the photo) — both apply independently to the same scenario. EDPB Guidelines 3/2018 is the authoritative source; see [GLOSSARY.md](../GLOSSARY.md) for the plain-language terms.

## Privacy and safety

- Applies to every change, not just ones that look security-related (see CLAUDE.md's "Security and privacy first" rule). Ongoing threat/concern tracking and open security questions live in [../security/README.md](../security/README.md), kept separate from this file's hard rules so this section doesn't grow into a running log.
- This app extracts and stores EXIF/GPS metadata from personal photos (see `app/gpsdata.py`). Location data is sensitive by default — never transmit, log, or expose it more broadly than the feature being built strictly requires.
- **Closed-by-default (project-wide)**: no photo or user data ever leaves the server the user controls. No cloud APIs, no telemetry. Applies to every topic folder, not just photo-server (whose own README.md states this same rule for its scope — this is the source of truth it inherits from). Sole exception: Let's Encrypt certificate issuance for HTTPS.
- **General rule, not just Android (raised 2026-09-04)**: any host platform's own "convenient" backup/sync feature is a real, easy-to-overlook leak path for this project's locally-stored sensitive data (labels, embeddings, tokens) — check explicitly, don't assume "stored locally" means "stays local." Concrete instance: a native Android app's automatic backup-to-Google-Drive sweeps an app's local data unless excluded (`android:allowBackup="false"`, [security/THREATS.md](../security/THREATS.md) row 17) — iOS's iCloud app-data backup is the same risk class on that platform. **Not every local-storage mechanism carries this risk**: verified 2026-09-04 that browser `IndexedDB`/site storage is *not* included in Chrome's own account-sync feature (which only syncs bookmarks/history/passwords/settings) — so a browser-based (PWA) component storing sensitive data in `IndexedDB` structurally avoids this specific leak path, unlike a native app's local database. This is a reason to prefer a browser-based/PWA component over a native app where the choice exists, on top of [curation/ARCHITECTURE.md](../curation/ARCHITECTURE.md)'s existing PWA-over-native decision for phone-side inference — but always verify the specific platform/storage mechanism in use, don't assume the Android/Chrome findings above transfer to every future case unchecked.
- The planned distributed-sync/shared-storage feature (see [../distributed-sync/README.md](../distributed-sync/README.md)) means this project will eventually hold other people's files and metadata on infrastructure the user partially controls, and vice versa. Any design work in that area must treat "whose data is this, and who can see it" as a first-class question, not an afterthought — even before the architecture is finalized.
- **Moderation supersedes ownership, unconditionally**: a photo's strict/free sharing terms ([upload-and-share/OWNERSHIP.md](../upload-and-share/OWNERSHIP.md)) govern who may see or redistribute *legitimate* content — they never govern illegal or abusive content (CSAM, non-consensual imagery, harassment), which an admin-level perceptual-hash blocklist removes network-wide regardless of any owner's or sharee's claimed rights. Decided 2026-07-26, raised repeatedly and independently during that design conversation.
- **Legal reporting obligations, flagged not resolved**: once any feature lets a person upload without identity verification (the event/party "free-for-all" mode being the concrete case, see [upload-and-share/EVENTS.md](../upload-and-share/EVENTS.md)), this project likely takes on real legal duties around illegal content that a lawyer, not an engineering session, needs to confirm before that mode ships for real. The applicable reporting regime is Swedish/EU, not researched yet — don't assume NCMEC's US framework transfers. Don't treat the moderation mechanism above as legal clearance either way.

## Resource efficiency

- **Hard constraint (2026-07-17), not a preference**: all code must stay resource-tight — CPU, RAM, and disk. Reason: the target hardware isn't just today's server (see the `hardware` repo's `server/192.168.1.10/`) — this is meant to eventually run on genuinely constrained devices, Joakim's own example being a Raspberry Pi 3 (1GB RAM, ARM, no meaningful CPU headroom). Code that's "fine" on a beefy dev machine or even today's server can be a hard blocker there. Applies to every choice, not just ones that look performance-related: dependency picks (prefer lean deps over heavy ones for equivalent functionality), algorithms (avoid loading full datasets into memory when streaming/chunking works), container sizing (`mem_limit`s should reflect genuine need, not headroom-for-its-own-sake), and image processing specifically (this project already does Pillow-based thumbnail generation — CPU/memory-heavy per call by nature; cache aggressively, don't regenerate needlessly).
- Not yet done: an actual resource budget per target device (e.g. "must run the full stack under 1GB RAM on ARM") — until that's defined, treat "tight" as a design bias to apply on every change, not a measurable gate to check against. Define the real budget once there's a concrete Pi-class target to test against, not before.

## Vendor lock-in and openness

- **Standing principle (2026-07-18), not an absolute ban**: prefer open, non-proprietary, vendor-neutral tools and formats over ones from a single controlling company, even when the proprietary option is technically stronger — Joakim's reasoning: lock-in shows up regardless of a vendor's short- or long-term intent, and openness itself is the better trade even on pure UX/cost/control grounds, not just an ethical stance. Concretely: when a technology choice has a genuinely open, vendor-neutral alternative (e.g. Selenium vs. Microsoft-driven Playwright, an open dependency vs. a proprietary SaaS), default to the open one and name the trade-off explicitly if going proprietary anyway — don't default silently to whichever tool is best-known or easiest to reach for.
- **Not absolute**: this repo already depends on GitHub (Microsoft-owned) for hosting - Joakim is aware and has independence plans (own VPS, own git server) already in motion, not a contradiction to resolve today. The principle guides new choices going forward; it doesn't mandate ripping out everything already in place.
- Directly affects an open decision right now: Playwright (Microsoft) vs. Selenium (W3C standard, no single owner) for this project's first frontend test harness — see `gui/TODO.md`. Apply this principle when that gets decided, don't re-litigate the philosophy each time a similar choice comes up.

## Deployment and system access

- The AI session has no sudo access on the development machine and must never attempt system-level installs (Docker, database servers, network configuration, NAS OS setup, etc.). Such steps are always handed to Joakim as copyable commands.
- Deployment — of any kind, to any target — is always performed by Joakim, never automated by the AI session.
- **Hard constraint (2026-07-18): no toolchain gets installed system-wide on the dev machine, by Joakim or by the AI session — containers or per-project virtualenvs only.** Not just "the AI can't run the installer" (the point above) — Joakim doesn't want it run system-wide either, even by his own hand. Applies to every language's tooling (Python already follows this via `uv`'s per-project `.venv`, see `TOOLCHAIN.md`; the same bar applies to Node/npm, browser-automation tools, and anything else this project ever adds) and to existing code too, not just new work — retrofit when touched, don't grandfather it in. When a tool ships an official container image (e.g. Playwright's `mcr.microsoft.com/playwright`), prefer that over a host install even if it means an extra `docker run`/`docker build` step.
- **The AI session never handles real credentials** — account passwords, API keys, anything a human will actually keep using — not even in a local/disposable environment. Account creation (`server/scripts/create_account.py` or similar) always uses the tool's own interactive prompt with a human typing the value directly, or the command is handed over for a human to run — never a scripted CLI flag/env var the AI sets, never a real credential value stated or repeated in chat. **Why:** decided 2026-07-23 after exactly that happened creating this project's two real accounts locally — see `documentation/bugs/claude-bugs/fixed/2026-07-23-real-account-password-passed-via-scripted-cli-flag-and-repeated-in-chat.md`. Placeholder/fixture values that protect nothing reachable from outside the host (e.g. a local dev stack's fixed DB/JWT secrets) are a different category — the line is "would a human keep relying on this value," not "is it committed to a file."
