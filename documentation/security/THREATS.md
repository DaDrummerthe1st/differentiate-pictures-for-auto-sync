# Threats and security concerns

One row per concern — what it is, where it applies, current status. Analysis from
one design session (2026-07-27), not a systematic audit; see
[README.md](README.md)'s Status for how this relates to the eventual mechanical
scan pass. Severity is a rough call, not a scored methodology (no CVSS-style
framework adopted here — would be over-engineering for a pre-build design doc).

| # | Concern | Where it applies | Severity (rough) | Status |
| --- | --- | --- | --- | --- |
| 1 | A stored bounding box + tag text is a **labeled face-detection dataset**, more sensitive than the bare photo — if accessed or leaked, it's ready-made for facial-recognition matching in a way the photo alone isn't. | [tags/](../tags/README.md) bounding-box tagging (designed, not built) | High, if it ever happens — but gated behind this project's existing closed-by-default posture (POLICY.md) | Open. No extra protection specified for this data beyond the general closed-by-default rule; worth deciding whether it needs a *stricter* bar than ordinary photo data, not just the same one. |
| 2 | Client-supplied bounding-box coordinates need **server-side validation** (reject/clamp out-of-range or malformed boxes) once real endpoints exist. | [tags/](../tags/README.md), future `photo-server/` tagging endpoints | Medium — malformed input could break downstream crop/thumbnail generation, not a data-exposure risk by itself | Open. Not specified anywhere yet; flag when the real endpoint gets built (TDD: write the rejection-case test first). |
| 3 | Tag text is free-text, rendered back into a UI — classic **stored-XSS** surface if escaping is ever skipped in the real (non-mockup) implementation. | [tags/](../tags/README.md) tag text, any future GUI rendering it | Medium-High if missed — full account compromise potential in a browser context | Mitigated in `prototypes/mockup/` (`escapeHtml` on every interpolation) — mockup discipline only, not a guarantee about the real build. Needs the same discipline enforced (and tested) once real server-rendered/React UI exists. |
| 4 | **Third-party tagging consent gap**: a person can be identified, named, and graph-linked to other people's photos via tagging without ever agreeing to it. No design yet for her to see, object to, remove, or block being tagged. | [tags/TAXONOMY.md](../tags/TAXONOMY.md)'s people category, [tags/UX_FLOWS.md](../tags/UX_FLOWS.md)'s invite CTA | High for anyone tagged who isn't the tagger — this is the same problem Facebook's photo-tagging drew real regulatory scrutiny for | Open, undesigned. Closest existing partial answer: a *linked-account* person can presumably manage her own account's data once she registers; a *local-only* tag about her has no such recourse today. |
| 5 | **On-device detection model supply-chain risk** (DPFAS phase, not built): a tampered or poisoned model could mislabel content, including missing the automatic-privacy case (nudity/children's-photo auto-tagging, [tags/TODO.md](../tags/TODO.md)) it's meant to catch. | VISION.md Pillar 2's on-device inference, not started | High if it ever misses the specific case it exists to catch, but far off — nothing built yet | Deferred — real question once on-device inference is actually being built, not before. |
| 6 | **Facial-recognition/detection data security once storage is distributed** (DFS/"cloud" per-user nodes) — same data as #1, but now potentially reachable from hardware the *photo's subject* doesn't control at all. | [distributed-sync/](../distributed-sync/README.md) Pillar 1, explicitly out of scope for current design work (VISION.md) | High for the specific "publish embeddings network-wide" feature; Medium/resolved for plain redundant-copy storage | **Researched 2026-07-29** (authoritative sources — EDPB Opinion 11/2024, NIST SP 800-63B, peer-reviewed reconstruction-attack literature; see [TODO.md](TODO.md) item 6 for full findings). **Resolved**: owner-keyed encryption-at-rest (this project's existing "leased" tier) is the EU-regulator-validated baseline for redundant copies on hardware the subject doesn't control. **Still open**: the private cross-network face-matching idea ([../distributed-sync/METADATA.md](../distributed-sync/METADATA.md)) needs a decrypted embedding never to leave the subject's own device at all — the stronger cryptographic alternative (compare without decrypting) isn't proven to run on this project's target hardware yet. |
| 7 | `.githooks/pre-commit` (added 2026-07-27) runs with full local permissions on every commit — a hook is **arbitrary local code execution triggered by routine git usage**. | This repo's own dev tooling | Low today (it only runs the existing test suite, and changes to it show up in a normal reviewable diff) — but the risk *class* is real and grows with whatever gets added to the hook later | Accepted risk, noted for awareness. Re-evaluate before adding anything beyond test-running to this hook. |
| 8 | Ad-hoc dev/test servers (e.g. `python3 -m http.server` used to test `prototypes/mockup/`) bind a real socket for the session's duration. | AI session's own working habits, any project | Low currently (static mockup, fake data, localhost-only) — but the habit itself is what matters: the same pattern against real photos or real dev credentials later would not be low-risk | Mitigated in practice this session (confirmed killed via `pgrep` after each use) — not yet a written rule anywhere. Candidate for CLAUDE.md if this becomes a recurring pattern. |
| 9 | **This development machine itself can be compromised** (malicious dependency, compromised tool, physical access, anything) — the AI session's entire trust model assumes a clean host. | Everything, always | Unbounded in theory, unquantifiable here | Out of scope for this project's own docs to solve — general computing-security hygiene (patched OS, no untrusted installs outside per-project containers/venvs per POLICY.md's toolchain rule), not a project-specific design question. Named so it isn't silently assumed away. |
| 10 | **Account credential compromise undermines every other protection this design assumes.** Once an attacker authenticates as a user, she inherits that user's leased-tier decrypt keys ([../distributed-sync/OWNERSHIP.md](../distributed-sync/OWNERSHIP.md)), private tag visibility ([../tags/TAXONOMY.md](../tags/TAXONOMY.md)), and — if the private cross-network face-matching idea ([../distributed-sync/METADATA.md](../distributed-sync/METADATA.md)) is ever built — her private reference embeddings. | Auth system, every topic that assumes "only the legitimate owner" | High — this is the foundation every other protection in this design sits on | Open. No auth-hardening design exists yet (password hashing standard, rate limiting/lockout, session/token management, MFA). Raised 2026-07-28/29 during tag/sharing design — needs a real pass before any sharing/DFS feature ships for real, not an afterthought bolted on at the end. |
| 11 | **"Entity/identity squatting" — can one user's tag claim over a name, or over an animal she calls hers, let someone else "tap into" it?** Raised 2026-08-04 by Joakim as a direct question. Analyzed against the existing schema, not a new gap: `entities` rows are `owner_user_id`-scoped ([tags/SCHEMA.md](../tags/SCHEMA.md)) — a display name (e.g. two different users both typing "Joakim") never collides or merges across accounts, since there's no shared namespace to squat in. The only cross-account linkage point, `linked_account_user_id`, is set exclusively via an **email-bound invite** ([tags/SCHEMA.md](../tags/SCHEMA.md)'s `reference_kind='email'`) — the real person must control the invited inbox and actively accept, so a stranger typing your name into her own local entity gains no claim on your account. Animal/object/place entities never link to an account at all ([tags/TAXONOMY.md](../tags/TAXONOMY.md): "an object doesn't register an account") — there is no mechanism today by which another user "taps into" a pet entity you created; the one deliberate future exception (cross-household reuse) is opt-in-only per entity ([curation/IDENTITY_MATCHING.md](../curation/IDENTITY_MATCHING.md), resolved 2026-08-03). | [tags/SCHEMA.md](../tags/SCHEMA.md) entity linking, [curation/IDENTITY_MATCHING.md](../curation/IDENTITY_MATCHING.md) cross-household consent | Low — the design already closes this, verified rather than assumed | **Mitigated by existing design**, documented explicitly here for the first time. The genuinely open, adjacent risk is different and already tracked separately: **mislabeling** (threat #4's linked entry, [curation/RESEARCH_QUEUE.md](../curation/RESEARCH_QUEUE.md)) — a user asserting a false identity claim on someone *else's* photo, not squatting on the claimed person's own account. |
| 12 | **Loading a user-supplied pretrained model file is a code-execution surface, not just a content risk.** Raised 2026-08-04 (Joakim asked about bringing his own trained identity-detection model for comparison against this project's picks). PyTorch's default serialization (`torch.load` on `.pt`/`.pth`) is pickle-based — a crafted checkpoint file can execute arbitrary code the moment it's loaded, independent of what the model's weights actually predict. This is a different, worse category than a photo upload (which can be visually inspected/hashed) or even a malicious dependency (#5 above, which covers *this project's own* picked models' supply chain, not a third party's ad hoc upload). | Any future "bring your own model" comparison feature — not built, not designed | High if ever built without this constraint — full RCE on whichever host loads the file | Not built, so **currently theoretical** — flagged before the feature exists rather than after. If ever built: accept only formats that can't carry executable payloads (ONNX, safetensors — already this project's preferred runtime per [curation/DETECTORS.md](../curation/DETECTORS.md)/[curation/ARCHITECTURE.md](../curation/ARCHITECTURE.md)), never raw pickle/`.pt`, regardless of how trusted the uploading user seems. |

| 13 | **Free-text user feedback is a second stored-XSS-class surface, plus a new spam/abuse vector.** Raised 2026-08-05, [photo-server/DEFERRED.md](../photo-server/DEFERRED.md)'s feedback design. Same rendering risk as #3 (tag text) if escaping is ever skipped once an admin view renders it — but unlike a tag (visible only to the tagging user until she shares it), feedback is *authored by one user and rendered for a different, higher-privilege one* (the admin) by design, making a successful hit here more valuable to an attacker than a peer-to-peer tag would be. | Not built — see [photo-server/DEFERRED.md](../photo-server/DEFERRED.md) | Medium-High if missed, same reasoning as #3, elevated by the fixed admin-as-victim target | Not built, so currently theoretical — flagged before the feature exists. If built: escape on render same as #3, rate-limit and length-cap submission (`slowapi`, mirroring `/login`), and don't assume today's "everyone with an account is trusted household" threat model still holds once Pillar 3's less-verified upload modes exist. |
| 14 | **DDoS/resource-exhaustion risk accepted, not mitigated.** A real volumetric DDoS can't be stopped by anything configurable on an EdgeRouter X or in this app; that needs upstream mitigation (ISP-level, or a CDN in front), out of scope for this project's closed/no-cloud-APIs posture. | The whole deployed stack, once port-forwarded to the internet | Standing risk of self-hosting on a residential line at v1 scale | Accepted, not a today-fix. What IS mitigated: 2026-07-17's auth-gating work means almost every resource-expensive route (thumbnails, downloads, the full filesystem tree walk) requires a valid session, closing off anonymous abuse of those specifically — see [photo-server/DEFERRED.md](../photo-server/DEFERRED.md) for the two routes that remain anonymously reachable and why they're low-risk. |
| 15 | **The home server's router admin UI has no valid TLS** — `https://192.168.1.1` doesn't present a trusted certificate. | The EdgeRouter X's own web admin, LAN-only exposure | Low — expected for a home router's self-managed admin interface, not a live problem | Not a fix candidate, noted so a future session doesn't mistake it for one. |
| 16 | **Unbounded upload size on the new `detector` service's `POST /detect`** — an internal-network-only endpoint that reads an uploaded image into memory before decoding it; without a cap, an oversized body is a resource-exhaustion vector even though today's only caller (the future Phase 5 `auto_tag.py` orchestration job) sends known local photos, not attacker-controlled input. | `detector/main.py`, `documentation/curation/TODO.md` build-plan Phase 2 | Low today (internal-only, trusted caller), but real once any less-trusted caller could reach this service | **Fixed same day it was noticed** — `MAX_UPLOAD_BYTES` (env-overridable, default 25MB), enforced by reading in capped chunks so an oversized body is rejected (`413`) before a full read or PIL decode is attempted, not just checked after the fact. Test: `detector/tests/test_detect.py::test_detect_rejects_an_oversized_upload`. |
| 17 | **Contacts-import feature (flagged, not built) could leak *person↔photo association* to Google — a materially worse leak than contact-list access itself.** Raised 2026-09-04, Joakim's own framing: his concern isn't whether Google already has his contact list (unrelated — that's already true via the phone OS's own account sync, outside this project's control) but specifically that **Google must never learn which photos belong to which person**. That derived link is this project's most sensitive data category (same class as threat #1's "labeled face-detection dataset"). | [tags/TODO.md](../tags/TODO.md)'s "Contacts import" idea, [curation/IDENTITY_MATCHING.md](../curation/IDENTITY_MATCHING.md)'s face-labeling design | High if ever built without the constraints below — the whole point of a contacts-import feature is to associate a name (backed by a real Google-linked contact) with faces/photos | Not built, so currently theoretical — flagged before the feature exists, same shape as #12. **Two axes, not to be conflated (clarified 2026-09-04)**: how much of the address book the app ever sees, vs. whether the resulting person↔photo link can reach Google — hardening the first doesn't satisfy the second. **List-exposure minimization**: this project has no native mobile app planned at all (self-hosted web server, [../VISION.md](../VISION.md)), so the browser's **Contact Picker API** ([GLOSSARY.md](../GLOSSARY.md)) is the natural fit over Android's blanket `READ_CONTACTS` — each use is a deliberate, user-initiated selection (one or more contacts per invocation, via `multiple: true`) with nothing beyond the picked contact(s) ever disclosed to the app, no standing permission, no bulk list access. **Desktop gap, confirmed 2026-09-04**: Contact Picker API has **no desktop browser support at all** (Chrome on Android M+ only, plus an experimental Safari implementation, no iOS) — a session tagging faces from a PC/laptop (this project's photo-server already runs as an ordinary web app reachable from any browser) gets no contact-assisted suggestion at all there today; needs a documented fallback (plain typed name, or a one-time exported contact list a desktop session can search) rather than silently degrading with no explanation. **Fallback targeted 2026-09-05, reopens this row's exposure-minimization reasoning**: Joakim chose CardDAV (RFC 6352 — a real, widely-supported standard, confirmed via research, [../GLOSSARY.md](../GLOSSARY.md)) as the desktop mechanism, with a requirement that it re-sync rather than stay a frozen one-time export. CardDAV doesn't violate this row's "no Google-hosted inference, one-way only" constraints (still read-only, contacts-in-only) but it does trade the mobile picker's one-contact-at-a-time disclosure for standing app-password access to the *whole* address book — a bulk-exposure shape this row specifically picked the Contact Picker API to avoid. Not yet resolved whether that tradeoff is accepted for desktop specifically; see [../curation/IDENTITY_MATCHING.md](../curation/IDENTITY_MATCHING.md)'s "Contacts-import desktop fallback" section. **Corrected 2026-09-05**: Joakim questioned why Thunderbird never shows him an OAuth consent screen for Google CardDAV — confirmed Google supports an **App Password** ([../GLOSSARY.md](../GLOSSARY.md)) as a non-OAuth fallback needing no registered/reviewed app at all, same shape as iCloud's app-specific password; this row's mention of "OAuth" below was this session's own mistaken assumption, now fixed. Real build (Joakim generating an App Password against his own Google/iCloud account — the one step only he can do) deferred to a separate guided session, not attempted in this design pass. **Person↔photo link constraints, required regardless of picker choice**: (1) **one-way only** — contact names read in locally to prefill a name suggestion; nothing about photos, faces, or labels ever written back into the Contacts record (no notes/tags on the contact itself); (2) **no Google-hosted inference** — the actual face embedding/matching (MobileFaceNet, [curation/DETECTORS.md](../curation/DETECTORS.md)) stays self-hosted, never routed through a Google ML API, already required by this project's closed-by-default posture ([../policies/POLICY.md](../policies/POLICY.md)) but worth naming explicitly here since it's the exact mechanism that would leak the association if it slipped. **(3) Backup exclusion — structurally avoided by staying browser-based, confirmed not just assumed 2026-09-04**: `android:allowBackup="false"` ([GLOSSARY.md](../GLOSSARY.md)) only matters for a native Android app; verified Chrome's own account-sync feature does **not** include `IndexedDB`/site storage (only bookmarks/history/passwords/settings) — so a browser-based (PWA) component storing labels in `IndexedDB` never enters this leak path at all, a stronger guarantee than "moot until a native app exists." Re-evaluate only if a native app is ever built instead — see [../policies/POLICY.md](../policies/POLICY.md)'s new general rule on this. **That re-evaluation trigger fired 2026-09-05**: the project pivoted to a native Android app ([../VISION.md](../VISION.md), [../curation/IDENTITY_MATCHING.md](../curation/IDENTITY_MATCHING.md)'s "Reversed 2026-09-05" note) — this row's "(3) Backup exclusion" guarantee (structurally avoided by staying browser-based) no longer holds by default. `android:allowBackup="false"` ([GLOSSARY.md](../GLOSSARY.md)) becomes a required, not-yet-implemented setting for that app once contacts-import/face-labeling ships on it — flagged here so it isn't lost, not designed further in this pass. |
